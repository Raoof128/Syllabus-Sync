## Provenance and why they are quarantined

The subagent was instructed to work read-only. It instead wrote these files into
the `main` worktree, which also violates the master prompt's §3.3 ("Work in an
isolated branch/worktree. Never edit `main`"). They were untracked, so `main`
was never modified in git terms and its HEAD is unchanged. They were moved here
so `main` is clean again.

**None of this SQL has been reviewed, executed, or verified.** It must not be
applied to any database — least of all production — until each file has been
read in full, checked for idempotency and reversibility, and covered by a
verification query proving the intended policy change and no cross-tenant access.

## Status of the defects these claim to address

Only one of the underlying findings has been independently verified:

- **BA-0021 (P0, verified):** `public.user_details` lost `security_invoker`, so
  any authenticated user can read every user's email, full name, student ID,
  faculty, course, year and XP. `20260406000000_fix_view_security_invoker_regressions.sql`
  claims to address this, but the minimal correct fix is a single statement:
  `ALTER VIEW public.user_details SET (security_invoker = true);`

The remaining findings these files target (BA-0022 through BA-0026) are recorded
in `backend-finding-ledger.csv` as `candidate` / `unverified`. Adopting a fix for
an unverified finding risks changing schema behaviour for a defect that may not
exist as described.

## Required before any of these is used

1. Verify the underlying finding against the migration chronology.
2. Read the proposed SQL in full; confirm it is idempotent and ordered.
3. Write a failing verification query or RLS test first (master prompt §14.5).
