## Finding A — `SUPABASE_SERVICE_ROLE_KEY` read at module scope (admin.ts, and why its "siblings" are mostly false positives)

**Severity: P2** (real architectural risk with identified blast radius; not confirmed actively firing)

**Evidence.** `lib/supabase/admin.ts:3-4`:

```ts
const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL ?? '';
const supabaseServiceRoleKey = process.env.SUPABASE_SERVICE_ROLE_KEY ?? '';
```

These execute exactly once, whenever the ES module is first evaluated in the isolate — not per request.

I traced how OpenNext actually populates `process.env` under Cloudflare (`node_modules/@opennextjs/cloudflare/dist/cli/templates/init.js`):

```js
let initialized = false;
function init(request, env) {
  if (initialized) return;
  initialized = true;
  ...
  populateProcessEnv(url, env);   // process.env[key] = value for every binding/secret
}
export async function runWithCloudflareRequestContext(request, env, ctx, handler) {
  init(request, env);
  return cloudflareContextALS.run({ env, ctx, cf: request.cf }, handler);
}
```

`process.env` is populated as a genuine global mutation **once, on the first request the isolate ever handles**, before the Next.js request-dispatch/route code runs. Because Next.js/OpenNext lazily `require()`s route and library modules on first use (rather than eagerly bundling everything into the top-level entry chunk), `admin.ts` is — in the current architecture — very likely first evaluated _after_ `populateProcessEnv()` has already run, so the module-scope read today most likely captures the correct secret.

**Why this is still a real finding.** This only works by accident of lazy-loading order, not by design. It is the exact anti-pattern OpenNext/Workers best practices warn against ("never cache `process.env` at module scope; read it inside the request-scoped function"). It silently breaks if:

- any future code eagerly imports `admin.ts` from a path that's part of the Worker's top-level entry chain (a logger/telemetry bootstrap file, a barrel export, `instrumentation.ts` if one is ever added — there currently isn't one in this repo),
- or a future OpenNext/Next bundler change inlines more of the module graph into the eagerly-evaluated chunk.

**Blast radius (traced):**

- `lib/server/push.ts` → `createAdminClient()` — if the key is captured empty, `sendPushNotificationToUser()` silently no-ops (`subscriptionCount: 0`) for the isolate's entire lifetime. No error is thrown or logged beyond the one-time `adminWarningShown` console warning.
- `lib/services/rateLimitService.ts`'s `SupabasePostgresStore` constructor also calls `createAdminClient()`; if it returns `null`, the constructor throws, `getStore()` falls through to `MemoryStore`, and rate limiting silently degrades from a distributed store to an isolate-local one for that isolate's life (see Finding B — `failClosed` limiters remain safe, but `apiLimiter`/`mutationLimiter`/`bulkOperationLimiter` become bypassable across isolates).

**Failure scenario (conditions required):** a future code change causes `admin.ts` (or a module that imports it) to be evaluated before the isolate's first `populateProcessEnv()` call. Until then, this is latent, not active.

**Minimal fix:** convert `isAdminConfigured()`/`createAdminClient()` to read `process.env.SUPABASE_SERVICE_ROLE_KEY` and `NEXT_PUBLIC_SUPABASE_URL` **inside the function body** (matching the already-correct pattern in `lib/services/emailService.ts`'s `getEmailConfig()`), so every call re-reads current `process.env` rather than trusting a module-load-time snapshot. This costs nothing (it's a cheap string read) and removes the fragility entirely.

**Siblings actually checked and ruled out:** `lib/supabase/client.ts:3-4` and `lib/supabase/server.ts:4-5` read the same-looking module-scope pattern, but both vars are `NEXT_PUBLIC_*`, which Next.js's compiler inlines as literal strings at **build time** in every bundle (client and server) — there is no OpenNext runtime-env-population race for these, so they are not real instances of the same bug. `config/sentry/sentry.{server,client,edge}.config.ts:8` (`NEXT_PUBLIC_SENTRY_DSN`) are likewise build-time-inlined and not runtime-risk siblings. No other module-scope reads of a non-`NEXT_PUBLIC_*` secret were found anywhere in scope.

## Finding B — In-memory rate-limit fallback is isolate-local (already well-mitigated)

**Severity: P3** (documented, guarded, no confidentiality impact)

`lib/services/rateLimitService.ts` correctly prefers Upstash Redis → Vercel/Upstash-compatible KV → Supabase Postgres (via the admin client — see Finding A's blast radius) → in-memory `Map`, in that order, memoized in the module-scope `storeInstance` singleton (#10 in the table above). The in-memory fallback is explicitly documented as broken across serverless/Worker instances, and the code enforces **fail-closed** behavior at call time for security-critical limiters (`login`, `signup`, `passwordReset`, `passkeyAuth`, etc. — `config.failClosed: true`) when running in production with a memory store and no explicit override. Non-critical limiters (`apiLimiter`, `mutationLimiter`, `bulkOperationLimiter`, `failClosed: false`) remain bypassable by spreading requests across many Cloudflare isolates if the codebase ever ends up on the memory-store path in production — this is an accepted, clearly-logged tradeoff already, and Finding A is the only realistic way that path gets reached in production (since `SUPABASE_SERVICE_ROLE_KEY` is required-and-validated at deploy time by `tools/deployment/check-required-env.mjs`).

**Minimal fix:** none required beyond Finding A's fix, which removes the only realistic production trigger for this fallback.

## Finding C — Sentry init is a floating (`void`) promise, not tied to the request lifecycle

**Severity: P2** (plausible but not deterministic; degrades observability, not user-facing correctness)

**Evidence.** All three Sentry bootstrap files use the same shape:

```ts
// config/sentry/sentry.server.config.ts, sentry.edge.config.ts, sentry.client.config.ts
if (sentryEnabled) {
  void import('@sentry/nextjs')
    .then((Sentry) => { Sentry.init({ ... }); })
    .catch((error) => { console.warn('Sentry ... init failed:', error); });
}
```

This is module-top-level code (invoked once, when the module is first evaluated — for the server/edge configs, via Next's Sentry-SDK-generated instrumentation hook), and the promise chain is explicitly discarded with `void`, not `await`ed, and not passed to `ctx.waitUntil()`.

Per Cloudflare's own docs (`workers/runtime-apis/context/`, fetched during this audit): _"If the client is still receiving the response, including a streamed response body, the Worker invocation remains active without `ctx.waitUntil()`... Use `ctx.waitUntil()` for work that... may continue after a response is returned."_ This pattern is completely safe on a long-lived Node/Vercel process (which is presumably why it was written this way — it predates the Cloudflare port), but on Workers it depends on the dynamic `import()` + `Sentry.init()` microtask chain settling _before_ the isolate's first response finishes sending. If it doesn't, `Sentry.init()` may never complete for that isolate's lifetime, and even the `.catch()` warning may not fire.

**Failure scenario:** cold isolate's first request completes (response fully sent) before the dynamic import of `@sentry/nextjs` and subsequent `Sentry.init()` resolve. Error monitoring for that isolate then stays silently uninitialized — no exception, no log, nothing surfaces this. Given the app cut over to Cloudflare production _today_, this is exactly the window where operators most need reliable error visibility.

**Minimal fix:** `await` the dynamic import chain instead of discarding it with `void` wherever the surrounding code is already `async` (Next's instrumentation `register()` hook is `async`-compatible), or follow Sentry's dedicated Cloudflare-Workers-with-OpenNext integration guidance (`@sentry/cloudflare` / `wrapRequestHandler`, or explicit `ctx.waitUntil()` plumbed through OpenNext's context) rather than the generic Next.js template. At minimum, verify empirically post-cutover that Sentry events are actually arriving from the Cloudflare Worker (not just from residual Vercel traffic).

## Finding D — Push-reminder scheduling still runs through a separate GitHub Actions cron, outside the Cloudflare Cron Trigger migration

**Severity: P2** (concrete architectural inconsistency; user-facing impact depends on an unverifiable secret value)

`.github/workflows/push-reminders-cron.yml` polls an external URL every 10 minutes via `schedule: cron: '*/10 * * * *'`, independent of `.github/workflows/cloudflare-deploy.yml` and independent of the three `CRON_SECRET`-protected routes now dispatched natively via `wrangler.jsonc`'s `env.production.triggers.crons` → `custom-worker.ts`'s `scheduled()` → `lib/cloudflare/scheduled.ts`.

`wrangler.jsonc:63-67` explicitly documents the cutover: _"production scheduling moved from Vercel Cron to Cloudflare Cron Triggers. Vercel Cron was disabled first... so only one scheduler is ever active."_ That claim is true only for the three routes `runScheduledJob` knows about (`/api/auth/email/cleanup`, `/api/auth/password/cleanup`, `/api/security/rate-limit/cleanup`). Push reminders were never folded into `CRON_ROUTE_BY_EXPRESSION` and still depend on:

- `PUSH_REMINDERS_CRON_URL` (a GitHub Actions secret, value not visible from source) continuing to resolve to a live, correct origin post-cutover, and
- GitHub Actions' `schedule` trigger, which Cloudflare does not control and which GitHub explicitly documents as best-effort/delayable under load — a materially less reliable primitive than a native Cloudflare Cron Trigger for a feature (deadline/class/event reminders) that is otherwise fully native to this Worker.

**Two possible states, both plausible, neither confirmable from source:**

1. `PUSH_REMINDERS_CRON_URL` was already pointed at a stable custom domain that didn't change across the Vercel→Cloudflare cutover — in which case this is purely an architectural inconsistency (a second, less reliable scheduler still in use) with no active breakage.
2. It still points at the decommissioned Vercel deployment — in which case push reminders have been silently and completely dead since cutover, with the only signal being a failing (but likely unwatched) scheduled GitHub Actions run (`curl --fail`).

**Minimal fix:** fold push reminders into `CRON_ROUTE_BY_EXPRESSION`/`lib/cloudflare/scheduled.ts` and a fourth `wrangler.jsonc` cron trigger, matching the other three; retire `push-reminders-cron.yml`. Until then, at minimum verify `PUSH_REMINDERS_CRON_URL` resolves to the current Cloudflare origin.

## Finding E — `NotificationService` singleton is SSR-reachable across users (defense-in-depth gap)

**Severity: P3** (currently safe; fragile)

See table row #13. `export const notificationService = NotificationService.getInstance()` runs at module-evaluation time. Because the module carries `'use client'`, Next.js still executes it during server-side rendering of the initial HTML for every request whose component tree imports it — meaning the singleton object is constructed once per Worker isolate and is technically live across every subsequent user's SSR pass in that isolate, not just in the end user's own browser. Every mutating code path is currently guarded with `typeof window !== 'undefined'`/`navigator` checks, so no state actually flows into the shared `Map`s during SSR today — this is not an active leak. It is, however, one un-guarded future addition (e.g., "cache the current user's unread count on this singleton") away from becoming a genuine cross-user data leak, and the failure mode would be silent and hard to spot in review, since the existing 13 guard sites make the pattern _look_ safe by precedent.

**Minimal fix:** either lazily instantiate on first client-side call (`typeof window !== 'undefined' ? NotificationService.getInstance() : null`) instead of eagerly at module scope, or add a lint/CLAUDE.md note flagging this file as SSR-reachable so future edits keep every mutation guarded.
